# PMレビュー #08 — Phase 3 スクリーンショットの見た目レビューと、Phase 4 のアートディレクション

> 対象：`docs/screenshots/phase-3/` の13枚（コアのシェーダー3ティア、ヒーローのHTMLのみ版 ja/en×モバイル/デスクトップ、都市の俯瞰・中景・接近 × モバイル/デスクトップ）
> 位置づけ：Phase 4（デザインシステムと地表）の**デザイン上の要件**。§2 の `/ja` TBT 対策（PM_REVIEW_07）の後に着手する。都市（§5）は Phase 5 の地層4の要件だが、色の決め方がデザインシステムに関わるので先に示す。

## 0. 前提
- スクリーンショットの fps（3〜8fps）は、GPUのない環境のソフトウェア描画によるもの。**判断材料にしない。**
- 全体として、骨格は堅実で、文言・情報の階層も明確。ここからは「見た瞬間に記憶に残る」水準に引き上げる段階。

---

## 1. ボーリングコア（最重要の独自要素）

**問題**
- 太く短い円柱に、上面の同心円。**木の切り株・コルク・缶に見え、掘削したコアサンプルに見えない。**
- 1本が単色（砂色）なので、「通過した地層の色の帯が積み重なり、最後に自分のキャリアのコアが完成する」というコンセプトが画面から読み取れない。
- low は円周の分割が粗く、角張って見える。high の粒子感はサンドペーパーやコルクのように見える。**medium の質感がいちばん良いので、これを基準にする。**

**指示**
1. **細長い比率**：直径と高さの比を 1:4〜1:6 程度にする（実物のコアサンプルの比率）。
2. **端面は切断面**：上下の面の同心円をやめる（年輪に見えるため）。平らに研磨された切断面にし、側面の地層の縞が端面の縁まで続いて見えるようにする。
3. **掘削の痕跡**：側面にごく薄い水平のこすれ傷、端の縁に小さな欠け。どちらもシェーダーで描き、ジオメトリは増やさない。
4. **コンセプトの可視化（必須）**：通過した地層ごとに、その地層の色の帯がコアに積み重なる。まだ通過していない部分は、暗い影か細いガイド線だけにする。最後の地層を通過した時点で、11色の帯が揃ったコアが完成する。
5. **low ティア**：円周の分割数を48〜64に増やす（ジオメトリなので負荷は小さい）。
6. **high ティア**：粒子のスケールを細かくし、強さを半分程度にする。
7. **右端のナビゲーター**：小さな円柱を11個並べる今の形と、「1本の細長いコアが伸びていく」形のどちらがよいか、Phase 4 で両案のスクリーンショットを出して提案すること（BRIEF の「リングが積み重なる」と一致するのは後者）。

## 2. 地層の色
- 今の色（茶、青緑、セージ、スレートブルー、テラコッタ、砂、暗色系）は、土と岩の色として良い方向。このまま発展させる。
- **テラコッタの層が、危機を示す信号色（赤橙）に近すぎる。** 都市で汚染ファイルを示す赤と混同するので、テラコッタは錆色寄りにして彩度を下げる。
- 規則：**信号色（根拠＝シアン、危機＝赤橙、収束＝緑）は「光る・強調する」ときだけ使い、地層の色には使わない。**
- コアの中で帯を見分けられるよう、隣り合う地層の色の明度差を確保する（トークンの一覧に、隣同士のコントラスト比を併記すること）。

## 4. フォント（Phase 4-2 で2〜3案を提示する）
- コンセプト「原典」に合わせて、第一候補は次の組み合わせ：
  - **見出し＝明朝系**（公文書・原典の権威を感じさせる）
  - **本文＝読みやすいゴシック**
  - **数字とデータ＝等幅**
- 比較する案の例（ライセンス、サブセット後のサイズ、日本語と英語の字形の調和は、Claude Code が最新の情報で確認すること）：
  - **A 編集的**：見出し Shippori Mincho B1／本文 IBM Plex Sans JP／数字 IBM Plex Mono
  - **B 工学的**：IBM Plex Sans JP と IBM Plex Mono だけで構成し、見出しは太いウェイト
  - **C 読みやすさ重視**：見出し・本文 BIZ UDPGothic／数字 JetBrains Mono
- 同じヒーロー画面（ja/en × モバイル/デスクトップ）のスクリーンショットで比較できるようにし、案ごとにフォントのバイト数と LCP への影響を添えること。ウェイトは最大3つ、使う文字だけにサブセット化する。

## 5. 都市（Phase 5・地層4の要件。色の決め方は Phase 4 のトークンに反映）

**問題**
- 単色の箱が規則正しく並んでいるだけで、棒グラフやブロック玩具に見える。「10年以上増築を重ねた、無秩序なシステム」に見えない。
- 暖かいモーブ色の建物が、赤橙の汚染ファイルと色で競合している。
- 遠景のブロックが板チョコのように見え、ブロック化の境目がはっきり見える。

**指示**
1. **意味のある配置**：模擬データでも「コードベースの地図」として読めるようにする。
   - 区画＝ディレクトリ（区画の大きさ＝ファイル数、入れ子の小区画）、建物の高さ＝ファイルサイズ、幹線道路＝主要な処理の流れ（予約フォーム4系統、管理画面3種、Cron 6本など、ファクトシートの構造の数を使ってよい）。
   - 区画の形・大きさ・向きを不揃いにする。古い区画（低層で密）と新しい区画（まばらで高い）の対比で、増築の歴史を表す。
2. **色と光**：建物は寒色寄りの暗い無彩色（青灰）にし、**汚染ファイルの赤橙だけが唯一の暖色として際立つ**ようにする。
3. **夜の街**：窓のかすかな光（シェーダーで点を描くだけ。ジオメトリは増やさない）、距離と高さによるフォグ、建物の根元を暗くする擬似的な陰影。
4. **ブロック化の境目**：フォグとディザリングでなじませる（PM_REVIEW_06 §2 の指示どおり）。
5. 性能：上の表現はすべてシェーダーの範囲で行い、描画回数と三角形数を増やさない。
