## 0. 要約

- **総見積：約28〜33日相当**（1日＝8時間の実装・検証作業。オーナー／PMのレビュー待ちは含まない）。最大の山は Phase 5（各地層、約14〜16日）。
- **設計の柱（3つ）**
  1. **「HTMLが本体、3Dは後から差す」二段構成。** 初期描画は RSC/SSG の HTML だけ。Lenis・GSAP・three.js は load 後に「演出バンドル」として遅延読込し、static ティアでは一切読まない。
  2. **ピン留めは JS ではなく CSS `position: sticky`。** 各地層の高さを CSS で確定させ、ScrollTrigger は進捗を読むだけに使う。CLS が原理的に起きず、JS なしでも成立する。
  3. **単一 Canvas ＋ drei `<View>`。** メインシーンとボーリングコアを同じ WebGL コンテキストで領域分割して描く。シーンは「現在の地層±1」だけマウントし、離脱時の破棄をテストで検証する。
- **技術リスク TOP3**：① 45,000棟の都市をモバイル30fpsで描けるか ② 単一 Canvas でのシーン切替（シェーダーコンパイルの引っかかり・メモリリーク） ③ 初期JS 180KB と日本語フォントを抱えて LCP 2.5秒。①は Phase 3 に前倒しして使い捨てのスパイクで検証する。
- **ブロッカー：この開発機は GPU のない VM**（WebGL はソフトウェア描画になる）。fps と GPU メモリは**実機でしか測れない**。検証用の実機（iPhone／Android 各1台以上）を指定してほしい。
- **BRIEF・CLAUDE.md の矛盾・要確認：12件**（§6-A）。特に次の3つは該当箇所の実装前に解消が必要：
  - 外部リンクの許可が2つだけなのに、GitHub／DEV／LinkedIn を載せる仕様になっている（A1）
  - 25問レースの「3構成目」の正答率がファクトシートにない（A2）
  - 深層8案件の要約と技術スタックがファクトシートにない（A9）

## 2. アーキテクチャ方針の具体化（CLAUDE.md §3 の補足）

### 2.1 二段構成：「HTML本体」と「演出バンドル」

```
[初期] RSC/SSG の HTML ＋ CSS ＋ 最小のクライアント島
        ├ 現在の地層の判定（IntersectionObserver。数百バイト）
        ├ 根拠ドロワーの制御（<dialog>）
        ├ 言語切替・30秒ボタン・深度計
        └ ボーリングコアの HTML 版（ボタンの列。3D がなくても操作できる）

[load 後・アイドル時に読込／static ティアでは読まない]
  演出バンドル：Lenis ＋ GSAP/ScrollTrigger ＋ Stage（three/R3F）
        └ 各シーン：next/dynamic で「現在±1」だけ読込
```

- static ティア・reduced-motion・WebGL 非対応・JS 無効のいずれでも、全コンテンツが HTML だけで読める。
- 深度計とボーリングコアは初期から HTML 版で動き、演出バンドルが届いたら 3D 表示に切り替わる。

### 2.2 スクロール構造

- 各地層の `<section>` の高さは CSS 変数（例：`--layer-length: 300svh`）で SSR 時点に確定させ、内部の演出ステージは `position: sticky` にする。
- ScrollTrigger は**ピン留めに使わず**、`onUpdate` で「地層内の進捗 0〜1」を読むだけにする。pin-spacer の挿入によるレイアウトシフトが起きない。
- RAF は1本に統一する：`gsap.ticker` → `lenis.raf()` → `ScrollTrigger.update()` → R3F の `advance()`（Canvas は `frameloop="never"`）。
- タッチ端末では Lenis の `syncTouch` を切り、ネイティブスクロールのままにする（iOS の慣性スクロールと性能を優先）。
- iOS のアドレスバー伸縮による再計算は、`ScrollTrigger.config({ ignoreMobileResize: true })` と `svh` 単位で抑える。

### 2.3 単一 Canvas（`three/Stage.tsx`）

- 全画面固定の `<Canvas aria-hidden>` を1つだけ置く。drei の `<View>` で描画領域を分け、メインシーン（現在の地層のステージ要素に追従）とボーリングコア（画面右端）を同じコンテキストで描く。
- シーン登録表 `layerId → () => import(...)` を持ち、現在の地層 i に対して i-1・i・i+1 をマウントする。範囲外はアンマウントし、R3F が自動で破棄しないもの（自前で生成したジオメトリ・テクスチャ・RenderTarget）は各シーンの `dispose()` で明示的に破棄する。
- 次に入るシーンは、アイドル時に `renderer.compileAsync()` でシェーダーを事前コンパイルしておく（初回描画のカクつき対策）。
- WebGL コンテキストが失われたとき（iOS のバックグラウンド復帰など）は static ティアへ安全に切り替える。
- 開発用の計測 HUD（`?debug=perf`）：fps、draw call 数、三角形数、`renderer.info.memory`、推定 GPU メモリ、マウント中のシーン、品質ティア。

### 2.4 状態管理

- 依存を増やさないため、`useSyncExternalStore` を使った小さな自前ストアにする（`currentLayer`／`progress`／`quality`／`passedLayers`／`drawer`）。
- 毎フレーム変わる `progress` は React の再レンダリングを経由させず、購読側が ref で読む。

### 2.5 品質ティア（`three/quality.ts`）

| ティア | 判定条件（初期案） | 内容 |
|---|---|---|
| high | detect-gpu tier 3 かつデスクトップ | 全演出、ポストプロセス、DPR 上限 2 |
| medium | tier 2、または高性能モバイル | ポストプロセスなし、DPR 上限 1.5、独自シェーダー |
| low | tier 1 | テクスチャだけの軽量マテリアル、DPR 1、粒子数を削減 |
| static | tier 0／WebGL 非対応／`prefers-reduced-motion`／`Save-Data`／JS 無効 | 3D なし。各シーンの静止画＋HTML |

- detect-gpu は既定で外部 CDN からベンチマークデータを取得するため、`benchmarksURL` で自サイトの `/gpu-benchmarks/` を指す（第三者への通信をなくす）。
- 実行中に fps が閾値を下回り続けたら1段下げる（drei の `PerformanceMonitor`）。
- テスト・デバッグ用に `?quality=high|medium|low|static` で手動上書きできるようにする。

### 2.6 コンテンツと数値（`src/content/`）

- `schema.ts`：`Confidence = 'measured' | 'approx' | 'reconstructed'`、`Evidence`（何を・どう測ったか／確度／出典＝ファクトシートの該当行／図表データ）、`Metric`（値・単位・表示形式・`evidenceId`）、`Layer`。
- ビルド時の検証（失敗したらビルドを止める）：
  1. zod によるスキーマ検証
  2. すべての `Metric.evidenceId` が実在すること、ID の重複がないこと
  3. **ja と en で ID の集合と数値が完全に一致すること**（翻訳時の数字ズレを防ぐ）
  4. **ファクトチェック lint**：コンテンツ中の数値がすべて BRIEF §6 に現れるかを照合する（創作された数値の機械的な検出）
  5. 本番ビルドでは `TODO(fact)` が残っていたら失敗、開発ビルドでは警告にとどめる
- 数値の描画は `<Metric>` だけに限る。地層コンポーネント内に数字が直書きされていないかを検証スクリプトで検出する。
- アニメーションで数字が増えていく演出（カウンター、正答率の推移など）は、最終値が必ず `Metric` の値と一致するように作る。

### 2.7 根拠ドロワー

- `<Metric>` はサーバーで描画する `<button>`（値＋確度バッジ）。ドロワー本体はネイティブの `<dialog>` を使い、`showModal()` でフォーカストラップ・Esc で閉じる・背景の操作無効化をブラウザ標準の機能で得る。閉じたら呼び出し元のボタンにフォーカスを戻す。
- 根拠の中身は HTML としてサーバーで描画する（検索エンジンとスクリーンリーダーが読める。JS にデータを載せない）。
- 図表はビルド時に生成するインライン SVG にする（チャートライブラリを入れない＝JS ゼロ）。
- `#evidence-<id>` で直接開けるようにする（「この数字の根拠はここ」を URL で共有できる）。

### 2.8 多言語

- next-intl で `/ja`（既定）と `/en` を `generateStaticParams` により両方静的生成し、`hreflang` を出力する。
- `/` だけ Accept-Language で振り分ける（Next 16 の `proxy.ts`。マッチャーを `/` に限定し、地層ページ自体は静的なまま）。
- UI 文言は `messages/{ja,en}.json`、地層のコンテンツは `src/content/layers.{ja,en}.ts` に置く。

## 4. 技術リスク TOP3 と検証方法

### R1：45,000棟の都市をモバイルで30fps以上で描けるか

**なぜ危ないか**

- 1棟を箱（12三角形）にしても約54万三角形になる。カメラが急降下すると画面の大半が建物になり、塗りつぶしの重なり（オーバードロー）が増える。
- 「赤く脈打つ」演出を CPU 側の行列更新で行うと、毎フレーム45,000件分のデータ転送が発生する。
- モバイルは発熱により数十秒後にクロックが下がる。短時間のベンチマークでは見逃す。
- この開発機には GPU がない。

**設計方針**

- 箱のジオメトリ1つ＋インスタンス属性（高さ・区画 ID・状態フラグ）。高さは頂点シェーダーで伸ばし、毎フレームの行列更新をゼロにする。脈動は `uniform time` と状態フラグだけで GPU 側で計算する。
- 区画ごとに InstancedMesh を分割（64〜256 チャンク）して視錐台カリングを効かせる。遠景は区画単位の低詳細ブロックに置き換える（LOD）。
- リアルタイムの影は使わない（シェーダー内の擬似的な陰影とフォグで表現）。DPR の上限はティアで制御する。
- 建物データはネットワークで送らず、シード付き乱数で生成する。高さの分布は `再現`。
- 棟数は全ティアで45,000を維持する方針。どうしても届かない場合の最終手段（low ティアで小さなファイルを束ねて描くなど）を採る場合は、根拠ドロワーにその旨を明記する。

**検証方法（Phase 3-9／3-10）**

1. 開発専用ページ `/lab/city` で、都市単体＋カメラの急降下＋脈動を実装する。
2. 計測 HUD で fps・draw call 数・三角形数・メモリを表示する。
3. 実機で**60秒の急降下ループ**を回し、平均 fps と下位1%の fps を記録する（発熱による低下も見る）。Android は Chrome のリモートデバッグ、iOS は Safari の Web Inspector を使う。
4. 合格基準：中位のモバイル実機で平均30fps以上を60秒維持／デスクトップで60fps／シーン固有の JS チャンクが250KB以下。
5. 不合格のときの打ち手の順番：DPR を下げる → LOD の切替距離を縮める → チャンク数を調整する → 遠景を板ポリゴンによる擬似表現にする → 最終手段。

### R2：単一 Canvas でのシーン切替（カクつき・メモリリーク・スクロール同期）

**なぜ危ないか**

- 次の地層に入った瞬間の動的 import とシェーダーコンパイルで、モバイルでは数百ミリ秒の停止が起こりうる。
- 破棄の漏れがあると、往復スクロールのたびに GPU メモリが増え、iOS ではコンテキストが失われる。
- Lenis・ScrollTrigger・R3F がそれぞれ RAF を持つと二重駆動になる。iOS ではアドレスバーの伸縮で再計算が頻繁に走る。

**設計方針**：§2.2〜§2.3（RAF の一本化、±1 の先読みと `compileAsync`、明示的な破棄、コンテキストロスト時の static 降格）。

**検証方法（Phase 3-10）**

1. 仮シーン（形は単純な図形だが、実シーン相当のテクスチャ・RenderTarget を持たせる）で全地層を構成する。
2. Playwright で「最上部 → 最下部 → 最上部」を3往復し、`window.__perf` の `geometries`／`textures`／`programs` がベースラインに戻ることを自動テストで確認する（リーク検知）。
3. PerformanceObserver で、切替時の Long Task（50ms 超）の回数と最大の長さを記録する。
4. 実機で往復スクロール中の fps と、Safari Web Inspector／Chrome DevTools でのメモリ推移を WORKLOG に記録する。
5. 合格基準：往復後にリソース数がベースラインに戻ること／切替時の Long Task が100msを超えないこと（目標値。実測後に調整を提案する）。

### R3：初期 JS 180KB（gzip）と日本語フォントを抱えて LCP 2.5秒

**なぜ危ないか**

- Next.js＋React の土台だけで初期 JS の大きな割合を占める（推定100KB前後。Phase 2 で実測）。
- GSAP＋ScrollTrigger＋Lenis を初期に読むと、さらに数十KB増える（推定）。
- 日本語フォントは1ウェイトでも数MBある。サブセット化しないと、LCP（ヒーローの文字）がフォント待ちになる。

**設計方針**

- RSC 中心にし、クライアント島は最小限にする。zod はクライアントに出さない。
- Lenis・GSAP・three.js は「演出バンドル」として load 後に読む（§2.1）。初期に必要なスクロール連動（深度計など）は IntersectionObserver で賄う。
- フォントは**実際に使う文字だけ**をビルド時にサブセット化（content と messages から文字を収集）し、woff2 を自前ホストする。ヒーローで使うウェイトだけを preload する。フォールバックフォントの字幅を合わせ、入れ替え時のレイアウトシフトを防ぐ。

**検証方法**

1. Phase 2-11：3D 以外の依存をすべて入れた状態で、Playwright により「最初の操作までに読み込まれた JS」の gzip 合計を測る（CI で180KBを超えたら失敗）。3D 以外の JS の総量もあわせて記録・報告する。
2. Lighthouse CI（モバイル、既定のスロットリング＝4G 相当、3回の中央値）で LCP／CLS／TBT を測る。
3. Phase 4-2：フォントのウェイトごとのバイト数と、LCP への影響を測って WORKLOG に記録する。
