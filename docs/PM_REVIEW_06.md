## 1. 評価
- 3-8：ティアごとの段階（high＝粒子感あり、medium＝独自シェーダー、low＝焼き込んだ小さなテクスチャ）と、通過直後のリングが1.6秒かけて発光から戻る演出は仕様どおり。
- 3-9：区画ごとのインスタンス描画、遠景のブロック化、毎フレームの建物単位の更新ゼロ、脈動をシェーダー側で計算する作り。設計は PLAN.md R1 の方針どおり。モバイル相当で最大約11万三角形、メインスレッドの負荷は1フレームあたり3.0〜7.1ms で、CPU 側には十分な余裕がある。
- 監査の指摘への対応（WebGL の判定用キャンバスの解放）も確認した。

## 2. 都市の30fps判定を Phase 6 まで持ち越す件
GPU のない環境では判定できないため、持ち越しは**やむを得ないとして承認**する。ただし、判定が遅れてもデザインをやり直さずに済むよう、次の3つを条件にする。

1. **代替案を今のうちに設計しておく**（3-10 の成果物）：iPhone で30fpsに届かなかった場合に切り替える、モバイル向けの軽い描き方を具体的に決めて WORKLOG に書く（例：遠景のブロック化をより手前から始める、急降下の到達点の近くだけを建物単位で描く、など）。
   - 条件：約45,000本という事実は崩さない（束ねて描く場合も総数は同じで、根拠ドロワーにその旨を書く）。
   - Phase 4・5 のデザインは、「モバイルで全建物を建物単位で近くから見せる」ことに依存させない。
2. **GPU 側の負荷の目安を測る**（3-10）：描画回数（モバイル相当の俯瞰と急降下）、急降下時に建物が画面を覆う割合（重ね塗りの目安）、フラグメントシェーダーの重さ。数値を WORKLOG に記録する。描画回数が多い場合（目安として150回超）は、区画の統合で減らせるかを検討する。
3. **本物の GPU で早めに確認する手段**：§4 のプレビュー環境ができたら、オーナーが自分のパソコンのブラウザで `/lab/city?debug=1` を開き、デスクトップの fps を測る。

Phase 5 に回す課題（俯瞰の格子が規則的すぎる、ブロック化の境目が見える）は承認。境目は、距離に応じたディザリングやクロスフェードでなじませること。

## 3. GitHub Actions が一度も動かない件
- Claude Code が調べること：
  - `gh api repos/senpythondev/Takefumi-portfolio/actions/permissions` などで、Actions の権限と、使える action の制限を確認する
  - ワークフローに `workflow_dispatch` を追加して `gh workflow run` で手動実行し、返ってくるエラーの内容を報告する
- オーナーが確認すること：リポジトリの Actions タブに表示される警告、アカウントの Billing（支払い情報や利用上限）の警告。
- CI が動くまでの扱い：TBT はローカルで5回測った中央値を「ローカル計測（CPU共有のため参考値）」として記録する。Phase 3 の完了は止めない。ただし、**Phase 6 の前までに CI が動いていること**を必須とする。

## 4. プレビュー環境（提案。オーナーが決める）
- Vercel にプレビュー環境を用意し、push のたびに確認用のURLができるようにすることを提案する（本来は Phase 7 の作業の前倒し）。
- 利点：
  - オーナーが自分のパソコンのブラウザ（本物の GPU）で、進み具合と fps を確認できる

- `/lab/city` は、プレビュー環境でだけ有効にする（環境変数で制御し、本番のビルドには含めない現状を維持する）。
- プレビューのURLは、Vercel のアクセス保護をかけたままにする（一般に公開しない）。
- オーナーが了承したら、Claude Code が手順を案内する。

## 5. 3-10 の範囲（まとめ）
1. 代わりの計測（PM_REVIEW_03 §8）：4倍・6倍のCPUスロットリング＋モバイルのエミュレーション、WebKit
2. 操作直後の Long Task を1回あたり100ms以下にする（PM_REVIEW_05 §3.2）
3. `/ja` と `/en` の TBT の差の原因調査（PM_REVIEW_05 §3.3）
4. 都市の代替案の設計と、GPU 側の負荷の目安の計測（本レビュー §2）
5. **detect-gpu をやめられるかの評価**：ベンチマークデータのダウンロードは端末によって最大156KBになる。実機に頼らない方針（モバイルは安全側から始め、`PerformanceMonitor` で自動調整する）になった今、detect-gpu の価値は小さい。次のような簡単な判定に置き換えた場合と比べて、評価すること：
   - static：reduced-motion、`Save-Data`、WebGL2 非対応
   - タッチ端末：medium から開始
   - デスクトップ：high から開始
   - 実行中は `PerformanceMonitor` で上下させる
   明確な利点がなければ、detect-gpu は外す（依存とダウンロードが1つずつ減る）。
6. CI の調査（本レビュー §3）
