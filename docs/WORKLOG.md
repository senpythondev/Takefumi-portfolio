### CI が動かなかった原因と対処

### PM への報告・提案
1. **CI の正式な TBT：`/ja` 281ms（予算 200ms）で不合格。** 原因は ja/en 共通の、ページ全体のレイアウトとハイドレーション。対策の候補（効果の大きい順）：
   - A. **根拠ドロワーの遅延読み込み**：ドロワーを別の静的な文書に分け、最初に数字を押したときに読み込む（JS なしでは根拠のページへのリンクとして動く）。HTML とペイロードが約半分になり、TBT がローカルで約2割下がった（実験値）。
   - B. 画面外の地層のレイアウトを省く仕組みを、位置の問い合わせが重ならない形で入れ直す（Phase 2 で取り消した `content-visibility` の改良版）。
   - C. 静的な部分のハイドレーションを減らす（React の流儀から外れるため最後の手段）。
   - Phase 4 でフォントとレイアウトが変わると数値が変わるので、A を Phase 4 の最初に行い、CI で効果を確認することを提案する。
2. **操作直後の Long Task**：3D基盤チャンクの評価（4倍で約 210〜245ms）だけが目標の 100ms を超える。選択肢：(i) three.js と描画を Web Worker（OffscreenCanvas）に移す（メインスレッドから評価と描画がなくなるが、drei の `View` は DOM に依存するため作り直しが大きい）(ii) 既知の例外として受け入れ、Phase 6 の iPhone 確認で実測する。
3. 都市のモバイル代替案（代替案B）は上のとおり。

**サブエージェントの確認：**
- `confidentiality-guard`：**PASS**。WebGL のレンダラー名は訪問者のブラウザ内で品質の判定に使うだけで、送信も保存もしないことを確認。detect-gpu の削除で、第三者のサーバーへの通信がなくなった。**要オーナー確認：CLAUDE.md §2（技術スタック）と PLAN.md にまだ detect-gpu が書かれている**（文書の不整合。CLAUDE.md はオーナーの判断で更新する）。
- `perf-auditor`：**CI で予算を超えているのは `/ja` の TBT（281ms）だけ。** 3D の読み込み方、canvas が1つであること、現在±1を超えてシーンがマウントされないことをコードで確認。指摘：根拠ドロワーの遅延読み込み（ローカルで約2割減）だけでは、CI の 281ms が約 228ms になる見込みで **200ms を切れない可能性が高い**。最も大きいのはレイアウト（Style & Layout 約360ms）なので、対策 B（画面外のレイアウトを省く）も合わせて必要になりそう。
- **CI 4回目（`b2f942a`）**：E2E 70件合格。**WebKit のスモークテストで実際の不具合を検出**：iPhone 相当（393px）の `/en` が横に 7px はみ出していた（scrollWidth 400）。Chromium の同じ幅でははみ出さないため、CI の WebKit のフォールバックフォントで英語のヘッダー（名前＋「30-second summary」＋「日本語」、どれも折り返さない）が少し広く測られたのが原因と判断。→ ヘッダーで名前だけを縮められる要素にし（はみ出すときは省略記号）、狭い画面ではボタンの余白を詰めた。あわせて、前のステップが失敗しても予算と Lighthouse の計測は必ず走るようにした（`if: !cancelled()`）。
- **CI 5回目（`6bf9a19`）**：初期JS 137.3KB・3D基盤 195.4KB で予算は合格、Lighthouse は `/ja` の TBT 239.5ms で不合格（`/en` は合格）。E2E は 69件合格・**1件不合格：自動降格のテスト**（CPU 6倍で 90秒待っても canvas が static まで消えない）。E2E が落ちたため WebKit のステップは飛ばされた。
  - **原因を調べた結果、本番にも影響する不具合だった**：drei の `PerformanceMonitor` は `flipflops` の回数に「上げてよい」という合図をすべて数える。最上位の high ではこの合図は何も変えないのに数だけが増えるため、**滑らかに動いているデスクトップ（約58fps）が約10秒後に `onFallback` で high → low に落とされ、以後の調整も止まっていた**（ローカルで再現：10秒の時点で high → low）。CI の高速なランナーでは降格の前にこの合図が数えられ、low で固定されて static に届かなかった。
  - **対処**：段階の切替を自前の小さな関数（`createQualityGovernor`、`src/three/quality.ts`）に移した。数えるのは**実際に変わった切替**だけ、揺れと見なすのは**向きが逆になった回数**だけ。揺れが2回に達したら上げるのをやめるが、**下げる切替は常に通す**（負荷が続けば必ず static に届く）。drei の `flipflops`／`onFallback` は使わない。→ 修正後、同じ条件で 20秒間 high のまま。ブラウザを使わない回帰テスト3件を追加（`tests/e2e/quality-governor.spec.ts`：最上位で上げる合図が続いても変わらない／上げる合図のあとでも負荷で static まで下がる／揺れたら上げるのをやめ、下げるのは止めない）。
  - 自動降格の E2E は CPU 6倍 → **20倍**に変えた。このテストの目的は「降格の経路が壊れない」ことの確認なので、どの機械でも確実に遅くする。6倍で 40fps 以上を保てる高速な機械が medium のままでいるのは正しい動作で、それは PM_REVIEW_03 §8 の「25fps 以上」の側として `npm run perf` で計測する。
  - WebKit のステップにも `if: !cancelled()` を付け、前のテストが落ちても必ず結果が出るようにした。
- 補足：Playwright は実行のたびに `test-results/` を空にするため、`npm run perf` の JSON は後続のテストで消える。上の Long Task の数値は、計測した時点の出力から記録した。
