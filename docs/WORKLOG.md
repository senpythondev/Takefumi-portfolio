## 2026-11-19 — M1 の途中確認：第0〜2幕と旧パネルへのつなぎ（ブランチ `feat/m1-cinematic`）

**モデル：** Claude Opus 5.5（シーン・シェーダー・タイムラインも含めて全部。CLAUDE.md §5 では独自シェーダーは Fable 5.2 の担当だが、このセッションはオーナーの切替で Opus のまま進めた）

### やったこと
- **ホームを「幕」の構成にした**（STORYBOARD §3-1）。
  - 第1幕（地表、スクロール200画面分）と第2幕（分解、150画面分）は、全画面の枠を固定したセクション。
  - スクロールを戻すと、すべて逆再生される。
  - 固定するのは `<html data-cinema>` のときだけ。この印は、品質の判定で3Dが動くと決まってから boot.ts が付ける。
- **ヒーローの文字は固定しない。** 普通にスクロールして離れ、離れながら消える。
  - 理由：スマートフォンでは、ヒーローの文字が1画面より高い。固定すると下が切れて読めない。
  - 消え方は、文字の下端が画面の85%から35%の位置を通る間に決める。長いヒーローも読み終えてから消える。
- **ディレクター**（`src/three/director/`）を作った。
  - カメラは1つ、場面も1つ。壁（全画面のシェーダー）、11本の帯でできたコア、漂う塵がある。
  - 毎フレームの流れ：各幕のスクロール進み具合 → 臨界減衰のばね（重さ）→ `shotAt`（各ショットのキーフレーム。すべてイージング付き）→ uniform・変形・CSS 変数。
  - 地層ごとの仮置きのシーン（`src/three/scenes/*`）と `WorldView` は削除した（PM の M1 c）。
- **各幕の中身**：
  - **第0幕**：ポスターはボーリング孔なしで描き直した。読み込みの各段階が終わるたびに、CSS の線が孔を掘り下げる。表示は「掘削中 NN%」で、NN は実際の進み具合。3D が描かれたら、壁の孔がその深さから続きを掘る。
  - **第1幕**：
    - カメラが孔の口へ寄り、晶洞が脈打ち、櫓が揺れる。
    - コアが孔から引き抜かれる。地面より下は描かない。
    - コアは横倒しになって画面の中央へ弧を描いて移る。縦長の画面では立てたまま。
    - 見出し「{{career-years}}分の地層を、一本のコアに。」が、文節ごとに暗い状態から明るくなる。
    - 被写界深度、ブルーム、グレイン、周辺減光を使う。
  - **第2幕**：
    - 帯が軸に沿って離れ、切断面の縁から光が漏れる。
    - 各帯の上下に細い線とラベル（年代と案件名）を出す。横長の画面では上下に交互、縦長の画面ではコアを左に寄せて右側に出す。
    - **ラベルは地層の目次を兼ねる**（実際のリンクで、キーボードでも使える）。そのため、独立した目次のセクションはなくした。
    - 年代の数字は、現れるときに一瞬だけ回る（Active Theory の等幅ラベル）。回るのは aria-hidden の写しで、本当の文字は DOM に残る。
    - 最後にオークションの帯が回って、切断面をカメラに向ける。
  - **つなぎ**（PM の M1 c）：
    - 次のセクションがスクロールで入ってくる間に、帯が閉じ、コアが画面端のナビゲーターへ飛んで溶け込む。
    - 同時に、カメラが壁全体に引き、第1層の深さまで降りる。
    - 旧パネルの地層は、同じ壁の上にそのまま続く。仮置きの立体は出ない。
    - 30秒の要約と確度の凡例は、このつなぎのセクションに移した。
- **動きの質**（PM の M1 b）：直線的な動きや一定速度の動きはない。
  - スクロールの値は、すべて臨界減衰のばね（ω=6.5）を通す。動き出しは遅く、加速して、静かに止まる。スクロールに少し遅れて付いてくる。
  - キーフレームは、すべてイージングした区間。コアの移動は弧を描く。
  - 塵の動きは、粒ごとに速さが違い、揺らぐ。
- **static 版と reduced-motion 版**：同じ物語を縦に積んで見せる。順番は、ヒーロー、見出し、コアの静止画、分解の静止画、目次、要約、凡例。
  - 静止画は実際の場面を描き出したもの（`scripts/act-shots.mjs`、`ACT_BARE=1`）。
  - 静止画は 3D の経路では読み込まない（perf-auditor の指摘）。3D が動くかどうかは読み込みの後にしか分からないので、`<img>` の遅延読み込みでは間に合わず、読み込んでしまっていた。
  - そこで、静止画は CSS の背景にし、縦に積んだ表示に決まったとき（`html[data-stage='off']`）だけ付ける。枠の大きさはハイドレーションの時点で確保するので、画像が来ても何も動かない。JS がない場合は `<noscript>` の画像を使う。
- **コアの見た目を core-lab.png に寄せた**：
  - 層の色を土の色の方へくすませた。
  - 層理は、コアの軸に沿って波打つ。
  - 掘削の輪は、かすかで不規則にした。
  - 切断面は研磨した岩で、光が漏れるのは縁だけ。

  3. low ティアでは、最後の操作から1.8秒で描画が止まり、ばねが目標の手前で固まっていた。ばねが落ち着くまで描き続けるようにした。
  4. **CLS 0.95（Lighthouse、`/ja`・`/en`）**：
     - 原因：ハイドレーション時に `data-cinema` を付け、boot が static と判定してから外していた。外したとき、Chrome は固定枠の中にある第2幕のラベルを「画面の上から消えた」と報告した。実際の位置は、どちらのレイアウトでも画面の外だった。
     - 対処：`data-cinema` は、3D が動くと決まってから付ける。CLS は、static に落ちる場合も3Dで動く場合も、デスクトップとモバイルで 0.0000 になった。

  - `tests/e2e/acts.spec.ts` を新しく作った。内容は次のとおり。

### push 後の CI（`9a564a8`、実行 44502457619）と追加の修正
- **E2E：1件が時間切れ**（`stage.spec.ts` の「上下に3往復しても GPU の資源が増えない」、150秒）。
  - **環境による不安定（flaky）。** 資源の数の判定は失敗していない。
  - 幕の分だけページが長くなり、ソフトウェア描画のフレームとスクロールの各操作がメインスレッドを取り合う。ローカルでは約1分だが、遅いランナーで並列に動かすと150秒を超えた。
  - 時間の上限だけを300秒にした。判定は変えていない。
- **Lighthouse：static 版の TBT 298.5ms**（本当の問題、上記のとおり）。
  - 同じ速さのランナーで比べると、ホームのスタイル計算・レイアウトがこのブランチで増えていた（`/en` 169 → 317ms、static 版 293 → 376ms）。変更していない根拠ページは増えていない（114 → 102ms）。
  - **原因（本当の問題、修正済み）**：第0幕の掘削の値（`--drill`）を `<html>` に書いていた。ルートのカスタムプロパティを変えると、長いページの全要素のスタイルを計算し直す。
    - 実測（CPU 4倍）：`<html>` に書くと1回 26ms、`.world` に書くと 1〜2ms。
    - `/en` では読み込み中に3回、3D の経路では5回書いていた。
    - `.world` に書くように直した。`<html>` の `data-stage` に `:is()` を使った指定も、普通の指定に直した（属性の変更で全体の再計算にならないように）。
- **ローカルの Lighthouse で `/ja` の LCP が 4.4秒になる回があった（本当の問題、修正済み）**：
  - 実際のブラウザでの LCP は、ヒーローの文字で約450ms（CPU 4倍）。4.4秒は Lighthouse のシミュレーションの値。
  - 縦に積んだ表示の静止画を、スクリプトが読み込み中に要求していた。それが観測上の LCP より前に来た回は、シミュレーションがその前の JS をすべて LCP の計算に含めていた。
  - 静止画は、画面に近づいたときだけ読み込むようにした（IntersectionObserver で `data-near` を付ける）。読み込み中には要求しないこと、3D の経路では一度も要求しないことを、E2E で確かめる。
  - この開発機は今、負荷が高い（load average 約4）。そのため、根拠ページにも同じ二通りの LCP と、TBT 255ms の回が出た。CI の値を正とする。

### PM への報告・確認したいこと
1. **static 版の TBT**（上記）：上限は緩めず、ホームの DOM を小さくする作業（長文をケーススタディへ）で直す。それまで、遅いランナーでは CI が赤くなる。この進め方でよいか。
2. **CI の CPU スロットリングの倍率**をランナーの速さに合わせる提案（11-18、承認待ち）。合否の判定をランナーによらず一定にできるが、今より厳しくなる。
3. **3D の読み込み中の INP は、この開発機では確かめられない。**
   - 3D 基盤の評価が、CPU 4倍で 200〜300ms 前後の長いタスクになる（perf-auditor の計測）。
   - 3D は操作を待たずに読み込みの後すぐに始まるので、この間にタップすると反応が遅れうる。
   - 実際の端末では `?debug=1` の HUD に INP が出るので、オーナーの確認のときに見てほしい。
4. Active Theory の Work ページの動きの録画は、引き続きあるとよい（第4幕の前に）。

### §2-3 日本語固有のコスト（調査）
- **CI の `/ja` が重いのは、ページ全体の最初のレイアウトが長いため。**

### PM の判断（PM_REVIEW_07 §2-2・§3-2：実装しないことを承認）
1. **§2-2（`content-visibility`）は実装しない。**
   - 前提の「CSS で確定済みの高さ（`--layer-length`）」は存在しない。地層の高さは中身で決まる。
   - そのため `contain-intrinsic-size` は推定値にしかならず、Phase 2 の位置のずれが再発する。
   - フォントの対策の後も 200ms を超えたら、ハイドレーションの削減か、アイドル時に地層を1つずつレイアウトする方式を提案する。
